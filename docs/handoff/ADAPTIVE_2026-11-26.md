## 2. Audit summary

Reused existing infrastructure instead of duplicating it:

- `ModelProfile`, `HardwareProfile`, `WorkloadProfile`, `PerformanceIdentity`,
  and `PerformanceProfileStore` from the profiling foundation.
- `model_requirements` for file, tensor, and KV accounting.
- `support::model_execution_support` and the architecture registry.
- `RuntimePlan` requested/effective field statuses.
- `dense_residency` and the staging request path.
- `BenchmarkReport` and `InferenceService` readback (placement, staged layers,
  speculative statistics).
- `draft_vocabulary_compatible` for draft eligibility.

Gaps addressed:

- Hardware identity did not include driver, backend build, native contract, or
  CPU feature identity.
- There was no feature-level compatibility report.
- There was no admission classification separating estimates, assumptions,
  risk, and infeasibility.
- Recommendations were not connected to a bounded calibration loop.
- There was no persisted, explainable plan with confirmation, stale-plan
  rejection, and applied/verified field states.
- Recommendation used file size alone as the RAM-fit test, which misclassified
  models whose file barely fit but whose runtime overhead did not. It now adds a
  conservative 512 MiB planning overhead (KV remains a reported budget input).

## 3. Execution environment and invalidation

New module: `adaptive::environment`.

`ExecutionEnvironment` records:

- OS, kernel, RAMforge version
- native residency contract version
- optional native revision from `RAMFORGE_NATIVE_REVISION`
- registered backend names plus native GPU-offload availability
- NVIDIA driver version parsed from `/proc/driver/nvidia/version`
- stable CPU feature fingerprint
- a 64-bit FNV-1a display fingerprint

Volatile free RAM/VRAM are excluded. `HardwareProfile` now embeds this
environment and includes it in the hardware fingerprint, so a driver, backend,
CPU-feature, native-contract, or RAMforge-version change produces a different
identity.

`record_invalidation` reports `model_changed`, `hardware_changed`, and
`schema_changed` independently. `environment_changes` explains field-level
differences.

`PROFILING_SCHEMA_VERSION` is now `2`. Legacy store schema `1` still loads, but
records with `runtime_schema = 1` no longer match exact identities and are
therefore not silently reused; `save` upgrades the store schema to `2`.

## 4. Model capability and compatibility system

New module: `adaptive::capability`.

`resolve_compatibility` evaluates the features a proposed execution actually
needs rather than only the architecture name:

- CPU execution
- GPU offload
- GPU placement readback
- staged residency
- greedy speculative decoding
- speculative sampling (explicitly unsupported)
- MoE execution
- KV cache quantization
- draft vocabulary compatibility

Each feature reports `fully-supported`, `supported-with-limitations`,
`supported-unvalidated`, `unsupported`, or `insufficient-information`, with
provenance (`gguf-metadata`, `support-registry`, `machine-observation`,
`native-backend`, `measured-profile`, `heuristic-estimate`).

Important rules:

- GPU offload is `supported-unvalidated` even when native placement exists.
- GPU-targeted speculative decoding is `unsupported`; the current path is
  CPU-target-only.
- MoE staging is `supported-unvalidated`.
- Quantized KV is a reported memory/fidelity tradeoff, not an equivalence claim.
- A missing draft compatibility result stays `insufficient-information`.
- An unknown dense/MoE classification prevents a staged-residency claim.

The overall class is the worst requested-feature class, and reasons are
preserved for display.

## 5. Intelligent resource manager

New module: `adaptive::resource`.

`ResourceBudget` separates:

- exact file size
- KV cache bytes with exact/estimated/unknown certainty
- fixed runtime overhead estimate (512 MiB)
- draft model bytes
- resident model window for staged residency
- VRAM requirement for GPU placement, or staged VRAM window
- cgroup limit when observed
- advisory planning budget

Admission classes: `within-budget`, `within-budget-with-assumptions`, `risky`,
`infeasible`, `unknown`.

`enforceable` is always `false`; the budget is never described as OS isolation.

Staged residency is modeled explicitly. File size is not treated as resident
memory: the budget compares the bounded resident window plus non-reclaimable KV
and overhead. If the window exceeds available RAM but the non-reclaimable part
fits, the result is `risky` (file-backed pages must be reclaimed), not
`infeasible`. This corrected an initial misclassification of the validated 32B
out-of-core path.

Unknown KV remains unknown. GPT-NeoX still reports “KV head count is
unavailable”, and the plan keeps that limitation instead of inventing a value.

## 6. Adaptive inference engine

New module: `adaptive::engine`.

### Candidate generation

`generate_candidates` starts from a recommended baseline and adds only
meaningful variants:

1. speculative K = 4/8/12 when the target is CPU/staged and the draft is
   compatible (historically the highest-value general win)
2. logical-thread variant
3. quantized-KV variant
4. staged-residency variant
5. partial-GPU variant sized from free VRAM and per-layer file bytes

Each candidate carries its strategy, compatibility report, resource budget, and
one of: eligible, eligible-with-risk, rejected, unsupported,
insufficient-information. Infeasible budgets are rejected before execution.
Unknown admission is allowed only for the baseline.

Limits are explicit: maximum candidates, maximum experiments, minimum runs for
selection, minimum improvement, maximum variability.

### Measurement summary

`MeasurementSummary` records median/min/max generation tok/s, decode, prompt,
TTFT, PSS, acceptance rate, runs, condition, and variability in basis points.
It is derived directly from `BenchmarkReport`; missing fields stay missing.

### Multi-objective comparison

`compare_experiments` reports throughput gain, TTFT change, PSS change,
significance, and explicit tradeoffs. A candidate is significant only when:

- median gain ≥ 500 bps,
- at least two measured runs,
- and either the measurement ranges are separated or both runs are stable
  (≤1,000 bps variability).

Preferences (`throughput`, `balanced`, `latency`, `memory`) are applied through
explicit rules, not an opaque score. `balanced` rejects improvements with TTFT
>25% worse or PSS >20% worse. `latency` and `memory` require ≥95% of baseline
throughput before optimizing their objective.

`select_best` returns `None` with reasons when evidence is inconclusive. A
winner is labeled `measured` or `low-confidence`.

### Experiment states

`completed`, `inconclusive`, `failed`, `interrupted`, `unsupported`, `rejected`.
A failed candidate is not treated as evidence that the model or backend is
generally unsupported.

`CalibrationReport` records model/hardware/environment fingerprints, baseline,
experiments, comparisons, best selection, preference, limits, notes, and
limitations.

## 7. Confirmed execution plans

New module: `adaptive::plan`.

Lifecycle: recommendation → proposed plan → explicit confirmation → execution →
readback → applied/verified report → persisted measurement.

`AdaptivePlan` contains:

- plan id derived from model, hardware, environment, strategy, and workload
- model/hardware/environment fingerprints and full environment
- workload and strategy
- draft path/fingerprint
- resource budget and compatibility report
- explainable decisions with evidence and confidence
- risks and unknowns
- verification workload (prompt, max tokens, runs, warmup)
- `requires_confirmation` (validated to be true)
- status (`proposed` at creation)

`revalidate_plan` rejects a plan when the model, hardware, or environment
changed. `adaptive-apply` fails closed before execution when revalidation fails.

`applied_report_from_observation` classifies every requested field:

- `verified`: matched native readback or effective runtime plan
- `accepted`: native request accepted but no getter (KV dtype)
- `applied`: effective value differs but is present
- `requested`, `unsupported`, `rejected`, `unknown`

Aggregate status is `verified` only when every field is verified or accepted.
Otherwise `partially-applied` or `rejected`. Requested GPU layers that read back
as zero are reported `rejected`, never as success.

The runtime observation is extracted from the real benchmark report: effective
execution mode, native GPU layer count, output device type, effective
context/batch/ubatch/threads, staged layer count, draft presence, speculative
statistics, TTFT, and acceptance rate.

## 8. CLI

New commands:

```bash
# Inspect recommendation plus environment, budget, and compatibility
ramforge recommend MODEL.gguf --ram 10G --context 128 --threads 6 \
  --draft-model DRAFT.gguf --draft-tokens 12 --json

# Build an explainable plan (no execution)
ramforge adaptive-plan MODEL.gguf --ram 10G --context 128 --threads 6 \
  --draft-model DRAFT.gguf --draft-tokens 12 \
  --output /tmp/plan.json --json

# Bounded calibration; persists only completed measurements
ramforge adaptive-calibrate MODEL.gguf --ram 3G --context 128 --threads 6 \
  --draft-model DRAFT.gguf --draft-tokens 8 \
  --max-candidates 4 --max-experiments 3 --runs 2 --warmup 1 --max-tokens 4 \
  --performance-profile /tmp/profiles.json --report /tmp/report.json --json

# Explicit confirmation, execution, readback, and verification
ramforge adaptive-apply /tmp/plan.json --confirm --json
```

Safety behavior:

- `adaptive-apply` without `--confirm` refuses to run.
- A stale plan is rejected before any model load.
- Unsupported compatibility is rejected without execution.
- `adaptive-calibrate` rejects infeasible candidates and risky candidates
  unless `--allow-risky` is supplied.
- Nothing in `adaptive-plan`, `recommend`, or calibration changes model weights,
  quantization, sampling, or context semantics automatically.

## 9. Validation evidence

### Metadata and planning across architectures

| Model | Result |
|---|---|
| Qwen2.5-Coder-32B Q4_K_M | hybrid + staged + speculative K12 plan; budget `risky`; compatibility `supported-with-limitations`; not executed this session |
| Qwen2.5-7B Q4_K_M | staged 7B calibration with 1.5B draft; execution validated |
| Qwen2.5-1.5B Q4_0 | draft compatibility source for 7B calibration |
| SmolLM2-135M Q4_K_M | GPU plan applied and verified through native readback |
| GPT-NeoX-20B Q4_K_M | plan retained unknown KV accounting; no invented value |
| DeepSeek-Coder-V2-Lite Q4_K_M | MoE + staged plan; staging reported `supported-unvalidated` |

### Real confirmed application (SmolLM2-135M, GPU)

`adaptive-plan` proposed GPU placement, 31 layers, 6 threads, f16 KV, no
staging. `adaptive-apply --confirm` executed the plan and native readback
reported:

- status `verified`
- execution mode `gpu`, effective GPU layers `31`
- context/batch/ubatch `128/64/64`, threads `6`
- output device `gpu`
- KV dtype `accepted` (no native getter)
- measured 84.83 tok/s, TTFT 33,029,767 ns

This is a real inference validation of the apply/verify path. It is **not** a
broad GPU-performance claim: only this model and workload were measured.

### Calibration behavior

- SmolLM2 CPU/GPU candidate sweep: 305.50, 303.73, 264.89 tok/s; no candidate
  cleared the 500 bps threshold, so no winner was declared.
- 7B staged with 1.5B draft, one run each: baseline 6.77, K4 7.47, K12 7.87
  tok/s. The engine correctly returned “inconclusive” because one run is below
  the two-run minimum.
- 7B staged with warmup and two runs: baseline 7.67, K4 7.53, K12 7.59 tok/s.
  The engine declined to declare a winner. This is the intended conservative
  behavior: a prior single-run “gain” did not reproduce under repetition.

These results validate the calibration control flow, persistence, and
conservative selection. They do not establish a new universal throughput claim.

## 11. Limitations and remaining risks

- Only SmolLM2 GPU and 7B staged CPU inference were executed in this milestone;
  32B, GPT-NeoX, and DeepSeek2 plans were not re-benchmarked here.
- GPU execution is still labeled `supported-unvalidated` in general.
- KV dtype remains `accepted`, not verified; the pinned native revision has no
  getter.
- Resource budgets are advisory, not cgroup-enforced; staged residency relies on
  reclaimable file-backed pages.
- Calibration is deliberately bounded and single-workload; results are not
  reused across workloads or models.
- `adaptive-plan` uses the existing recommendation policy as its baseline; it is
  not a global optimizer.
- Driver version parsing is Linux/NVIDIA-specific; absence is reported as
  unknown, not guessed.
- The sample sizes used for manual calibration are small by design; the engine
  refuses to promote them when evidence is insufficient.
- `thin` performance records still lack per-run GPU utilization; VRAM evidence
  comes from free-memory snapshots and native placement, not a peak counter.

## 12. Deferred / blocked

Deferred by scope:

- context/cache redesign, multi-session scheduling, HTTP API, TUI/GUI, packaging,
  model download, plugins, RAG
- distribution-preserving speculative sampling
- GPU-target speculative verification
- automatic application without confirmation
- global optimizer or unbounded search

Blocked by current native capabilities or evidence:

- native KV dtype getter (accepted-only verification)
- driver/runtime version from forgeCORE (currently parsed from `/proc`)
- broad GPU/MoE performance validation (requires dedicated benchmark campaigns)
- GPT-NeoX KV sizing (missing `head_count_kv` metadata)
