# RAMforge Deep Technical Audit and Engineering Roadmap

**Date:** 2026-11-25
**Scope:** RAMforge, forgeCORE, and the pinned native llama.cpp checkout.
**Mode:** Audit, measurement, and research. No functional product changes.
**Primary question:** What actually limits the largest executable GGUF model and real
inference throughput on this machine, and what is the highest-value next work?

## 1. Executive summary

RAMforge is not blocked by an inability to *execute* oversized models. It is blocked
by three narrower problems:

1. **Capability gating is stricter than the native backend.** The pinned native
   llama.cpp already executes `deepseek2` MoE models; RAMforge's own registry marks
   them unsupported, so the most promising capacity architecture is unreachable
   through the product. **[V][M]**
2. **The safe adapter hides the controls that determine capacity and speed.** RAMforge's
   `ForgeCoreContextOptions` forwards only context length, thread count, and an optional
   trace size. KV-cache dtype, flash attention, batch/ubatch, and offload flags are
   hard-coded to `ContextOptions::default()` (F16 KV, auto flash attention, batch 2048).
   **[V]**
3. **Dense overflow is storage-bandwidth-bound, not compute-bound.** A 19.85 GB dense
   32B model runs, but at ~0.1 tok/s with 10.08 GB peak RSS and 19.2 GB of file reads.
   No amount of thread tuning fixes that. Capacity beyond RAM for dense models is a
   data-movement problem. **[M][E]**

The strongest concrete capacity findings are:

- **DeepSeek-Coder-V2-Lite (15.7B total, 64 experts, 6 active) executes natively at
  2.9 GB peak RSS**, with 2.3 s prefill and 0.26-0.70 s per decode token, entirely on
  CPU with mmap. RAMforge reports `forgecore_execution_supported: false`. Enabling it
  is the cheapest large-capacity win available. **[M][V]**
- **KV quantization is real and already supported natively.** For Qwen2.5-7B the measured
  KV slope is 57,356 B/token at F16, 30,476 B/token at Q8_0, and 16,140 B/token at Q4_0.
  At 131,072 tokens that is 7.52 GB / 4.00 GB / 2.12 GB. All variants decode correctly.
  RAMforge's planner assumes F16 and never forwards a KV dtype. **[M][E][V]**
- **Partial residency and standby work as documented.** After one cold transition, alternating
  Qwen layer selections read and transferred 0 bytes and completed in 0.26-0.31 ms, with
  1000‰ standby hit rate and 1.157 GB served from standby over the run. **[M]**

The most important caution is that **mmap is not RAMforge-controlled streaming**. The OS
chooses which pages to retain and which to fault back in. The 32B run demonstrates that
this still executes, but the resulting throughput is set by NVMe bandwidth divided by the
non-resident working set, minus whatever the page cache retains. **[V][M][E]**

**On 180B and 500B:** this audit produced no evidence that a dense Q4 180B model (~90 GB)
can run interactively on this machine. The measured dense storage floor implies roughly
0.02-0.1 tok/s at best for a 90 GB working set on local NVMe, before compute. **[E]**
A 500B Q4 model (~250 GB) is not supportable on this hardware at all with 15 GiB RAM and
4 GB VRAM. MoE is the only credible route to very large parameter counts here, and it
requires expert-level residency that does not exist yet. Any claim beyond "executes
slowly via demand paging" is unsupported.

### Top five recommended tasks

1. **Enable validated `deepseek2` MoE execution** in the support registry and tokenizer
   path (Track 1). Unlocks a 15.7B model at 2.9 GB RSS today.
2. **Expose and forward KV dtype, flash attention, batch/ubatch, and offload options**
   through `ForgeCoreContextOptions` and the runtime plan (Track 1/3). Unlocks 1.9-3.5x
   KV reduction and real prefill batching.
3. **Fix `run --backend forgecore` hard-coding `n_threads = 1`** (Track 1). A one-line
   correction to a severe CPU throughput bug.
4. **Replace advisory planning fields with enforced configuration and expert/KV-aware
   accounting** (Track 1). Removes the gap between reported and actual execution, and
   makes MoE capacity estimates meaningful.
5. **Make MoE residency expert-aware** (Track 2/3, strategic). This is the only path with
   a credible claim to 10x-class capacity beyond RAM; start with a read-only routing
   experiment, not a staging implementation.

### Highest-potential hypothesis

Expert-aware MoE residency: stage only the experts selected by the router for the current
token/batch instead of whole layers. DeepSeek2 activates 6 of 64 experts per layer; the
expert tensors are 7.58 GB of the 10.36 GB file, so whole-layer staging copies ~6x more
data than the active set. If a routing-observation hook can drive prefetch/stage decisions,
MoE decode could become I/O-light. This is unproven because no expert-granular native API
exists. See §11, H1.

### Biggest blocker

There is no native expert-routing or expert-granularity residency API. `llama.h` exposes
layer staging, tensor storage introspection, page residency, and KV/graph controls, but no
way to observe selected experts per token or to stage an individual expert. Whole-layer
staging copies every expert in the layer, destroying the MoE advantage. **[V]**

### 3.2 Actual execution paths

There are three distinct paths, and they do not expose the same capabilities:

1. **Legacy `run` (default `--backend legacy`)**
   `InferenceEngine` / `StreamingLlamaModel`: managed-memory ledger, layer streaming,
   own F32/quantized matvec. CPU only, `llama`/`qwen2` only. This is the historical
   out-of-core path. **[V]**
2. **`run --backend forgecore`**
   `Model::load` → `Context::open` → `Batch::decode` → logits → RAMforge sampling.
   Supports GPU placement via model options, but the context is opened with
   `n_ctx`, `n_threads: 1`, and trace only. No staging, no KV dtype, no batch control. **[V]**
3. **Service path (`serve`, `benchmark`, `staging-cycle`, `staging-probe`)**
   `InferenceService`: plan, load model, open context with plan threads, configure
   staging pool/standby, stage layers, generate. This is the advanced path that all
   recent residency results use. **[V]**

A fourth surface, `machine`/`plan`, produces candidate plans and preflight estimates
but does not execute. It is where several "streaming" and batch claims originate, so it
is easy to over-read.

### 3.3 CLI surface relevant to this audit

`inspect`, `plan`, `support`, `storage`, `calibrate`, `calibrate-hw`, `machine`,
`profile`, `simulate`, `benchmark`, `staging-cycle`, `staging-probe`, `optimize`,

The CLI is broad. The audit found no dead feature that is harmful, but several
surfaces overlap in what they claim about placement and memory. See §4.3.

## 4. RAMforge architecture assessment

### 4.1 Layering is mostly correct

The stated boundary is respected in the code: RAMforge does not link `forge-sys`
directly, does not call llama.cpp FFI, and uses `forge_core` safe types. The adapter
(`forgecore.rs`) owns device validation, model loading, context opening, staging calls,
and lifetime state. That is the right shape. **[V]**

The service boundary is also right: CLI/TUI clients talk to `InferenceService`, which
owns planning, staging, and generation. Future work should extend this boundary rather
than add another execution stack.

### 4.2 The adapter is the throughput and capacity bottleneck

`ForgeCoreContextOptions` has exactly three fields:

```rust
pub struct ForgeCoreContextOptions {
    pub n_ctx: Option<u32>,
    pub n_threads: usize,
    pub trace_max_events: Option<usize>,
}
```

`RAMforge/crates/ramforge-runtime/src/forgecore.rs:541-550` **[V]**

`open_context` starts from `forge_core::ContextOptions::default()` and overrides only
those three fields (`forgecore.rs:510-537`). Consequently every context opened through
RAMforge runs with:

- KV cache `type_k = F16`, `type_v = F16`
- `flash_attn = Auto`
- `n_batch = 2048`, `n_ubatch = 512`
- `n_seq_max = 1`
- `offload_kqv = true`, `op_offload = true`

forgeCORE already supports all of these (`forgeCORE/crates/forge-core/src/context.rs`,
`ContextOptions` is `#[non_exhaustive]` but public and mutable). The missing piece is
purely RAMforge-side plumbing. This is the single highest-leverage safe change in the
codebase. **[V]**

### 4.3 Planning fields are partly fictional

`runtime_plan.rs` computes an `EffectiveRuntimeConfig` containing `batch_tokens`,
`ubatch_tokens`, `sequence_max`, `kv_type_k`, and `kv_type_v`. The audit found:

- `batch_tokens` defaults to `1` (`runtime_plan.rs:201`) and is clamped to context.
- `ubatch_tokens` is set to the **full context length**, not a micro-batch
  (`runtime_plan.rs:433-435`). This is not a native ubatch setting.
- `kv_type_k`/`kv_type_v` are hard-coded strings `"f16"` (`runtime_plan.rs:436-437`).
- None of these values are forwarded by `open_context`.

So the plan reports configuration that the execution path does not apply. `--json`
output can therefore mislead an operator into believing batching or quantized KV is
active when it is not. This is a correctness-of-reporting problem, not just a missing
optimization. **[V]**

`execution_candidate.rs` similarly offers a `MappingStrategy::Streaming` candidate
(`execution_candidate.rs:242`) that no executor implements. It is a hypothetical plan,
not a streaming runtime. **[V]**

### 4.4 Thread semantics

`runtime_plan.rs:175-215` selects physical cores for Maximum Performance/Balanced/Custom,
falls back to logical availability when topology is unknown, and clamps to available.
This is a sound default and matches the measured direction (§8.4). **[V][M]**

But `run --backend forgecore` ignores the plan entirely:

```rust
.open_context(ForgeCoreContextOptions {
    n_ctx: ctx,
    n_threads: 1,
    ...
})
```

`RAMforge/crates/ramforge-cli/src/main.rs:4524-4528` **[V]**

The service path correctly forwards `self.plan.effective.threads`
(`inference_service.rs:764-768`). So the same model can run at 6 threads through
`benchmark` and 1 thread through `run --backend forgecore`. This is a severe,
low-cost bug: a one-line change plus a regression test. **[V]**

### 4.5 Architecture gating

`support.rs` lists `llama`, `qwen2`, `gptneox`, `mistral`, `qwen3`, `qwen35`, `gemma`,
`phi`. `deepseek2` is absent. `model_execution_support` therefore returns
`forgecore_execution_supported: false` for the local DeepSeek model, and `plan` refuses
with an architecture-level reason. **[V][M]**

Native llama.cpp supports it (`native/src/src/llama-model.cpp:283` constructs
`llama_model_deepseek2`), and the isolated probe executed it successfully. The gate is
policy, not capability. This is the clearest example of RAMforge understating what the
backend can do. **[V][M]**

The registry's own design is reasonable: inspect/plan are generic, execution is
validated per architecture, and unsupported combinations fail explicitly rather than
falling back. The fix is to add a validated entry, not to weaken the model.

### 4.6 Resource accounting

`model_requirements.rs` distinguishes file bytes, tensor payload, fully resident
weights, KV estimate, mapped-plus-KV, and unknown requirements. That taxonomy is good
and should be preserved. **[V]**

Limits:

- KV estimate is `elements × kv_bytes_per_element` with a default of 2 bytes and an
  explicit assumption that batch is **not** included (`model_requirements.rs:113,121,307`).
  It can represent quantized KV but no caller sets it. **[V]**
- `fully_resident_weight_bytes` counts the entire tensor payload. For MoE it counts all
  64 experts, not the 6 active. That overstates the active working set and hides the
  actual opportunity. **[V][M]**
- It does not model expert routing variability, shared experts, or per-token expert
  reuse. A capacity estimate for MoE therefore cannot currently answer "what must be
  resident to decode one token?" **[V]**

### 4.7 Verified strengths worth preserving

- Explicit failure on unsupported device/backend/architecture; no silent CPU fallback. **[V]**
- Native lifetime/quiescence contract before eviction; release gated on `EBUSY`. **[V]**
- Delta transitions preserve shared layers and transfer only the difference. **[M]**
- Bounded standby cache with 100% hit rate on alternating selections. **[M]**
- Direct positional reads into pinned memory and coalesced GGUF ranges. **[V][M]**
- CUPTI tracer exists and is usable, with documented graph-mode limitations. **[M]**

### 5.3 What is inherently llama.cpp/ggml

- Kernel math, quantization kernels, graph construction, scheduler, and backend split.
- Which experts the router selects and how MoE matmuls are dispatched.
- CUDA graph capture/replay and most synchronization.
- KV cache allocation layout inside the context.
- The decision to touch a mapped page during CPU compute (demand paging).

RAMforge can prepare, place, stage, reserve, and observe around these. It cannot
substitute its own tensor engine or graph scheduler without violating the architecture
and duplicating a large, optimized native component. **[V]**

### 5.4 Boundary verdict

The boundary is sound and should not be changed. The gap is not architectural; it is
that the safe adapter exposes a small fraction of what forgeCORE already offers. The
correct next move is to widen `ForgeCoreContextOptions` and add capability reporting,
not to bypass forgeCORE. **[V]**

## 6. Overflow and residency analysis

### 6.1 Memory taxonomy (what is actually what)

| Layer | Owner | Controllable by RAMforge? | Notes |
|---|---|---|---|
| GGUF file on NVMe | OS/filesystem | Read patterns only | Source of truth |
| File-backed mapping | llama.cpp mmap + OS | `mmap` vs `mmap-no-prefetch` | Demand paging, not streaming |
| Page cache | OS | Advisory (`fadvise`, prefetch) | Retains hot pages; evictable |
| Host-resident tensors | llama.cpp/native | Partially (load mode, repack) | RSS-visible |
| Staged host buffers | RAMforge/native | Yes (pinned pool, coalescing) | Bounded |
| Device tensors (model) | llama.cpp CUDA backend | Layer staging only | Whole layers |
| Staging/standby device buffers | native staging pool | Yes (limits, delta commit) | Bounded, validated |
| KV cache | llama.cpp context | Dtype/length only | F16 today |
| Compute buffers / graphs | ggml backend scheduler | Indirectly (batch, backend) | Not per-tensor |
| RAMforge ledger | RAMforge | Yes | Logical, not RSS |

The important distinction: **a mapped model is not a resident model**, and **page-cache
residency is not RAMforge residency**. The planner's `mapped_weights_plus_kv_bytes`
deliberately includes only KV, with an explicit assumption that mapped weights are not
assumed resident (`model_requirements.rs:217-226`). That is honest and should remain. **[V]**

### 6.2 What happens on VRAM overflow

1. Model load places `gpu_layers` transformer layers plus output on CUDA0 according to
   native placement. **[V]**
2. Remaining layers stay CPU/file-backed. **[V]**
3. The service can stage additional whole layers into a bounded device staging buffer
   via `stage_layer_cuda` or the pending/delta path. **[V]**
4. Staged layers are not part of the model's static placement; they are substitute
   sources for the duration of a graph, and the graph must be invalidated before
   eviction. **[V]**
5. If the staging budget cannot fit the layer plus pool plus pending slot, the plan is
   rejected; there is no silent overcommit. **[V]**

**Important current restriction:** dynamic layer staging requires a **CPU plan**
(`gpu_layers = 0`) plus a separate selectable CUDA device for staging buffers. A GPU or
hybrid plan that already offloads layers rejects staging with
`"staged layers require a CPU plan; GPU/hybrid plans use normal placement"`
(`inference_service.rs:669-674`). So an operator cannot currently combine, for example,
20 statically offloaded layers with 8 dynamically staged layers. This is a real capacity
limitation, not just a configuration preference. **[V]**

Measured Qwen 7B staged configuration: 28 CPU layers, 8 staged layers of 131,135,488 B
each, CUDA0 model bytes 0 (staged buffers are separate), CPU_Mapped 4.677 GB, CPU KV
14.68 MB, CUDA0 free 2.718 GB. **[M]**

### 6.3 What happens on RAM overflow

There is no RAMforge-controlled host overflow path for native weights. When the model
exceeds available RAM:

- mmap pages are reclaimed by the OS and faulted back on access.
- The process does not get a clean "stage this layer into RAM" transaction.
- Throughput becomes a function of page-cache hit rate and NVMe latency/bandwidth.
- Major faults and file-system reads are the observable evidence.

The 32B dense run is the canonical example: 19.85 GB file, 10.08 GB peak RSS, 19,208
major faults, 19.2 GB read, 10.2-10.4 s per steady decode token. It executes, but the OS is choosing
what stays resident. **[M]**

This is why "mmap works" must not be presented as "RAMforge streams tensors efficiently."
The measured behavior is demand paging under pressure, with no prefetch guarantee and no
control over eviction order. **[V][M]**

### 6.4 What happens when both overflow

The process relies on the union of page cache + VRAM + any staged layers, with the OS
and native scheduler making most decisions. RAMforge can:

- Bound staged/standby VRAM.
- Prefetch advisory page ranges.
- Choose which layers to stage.
- Refuse plans that cannot fit configured budgets.

It cannot guarantee a working set, prevent page-cache eviction by other processes, or
provide hard real-time behavior. Under the audited desktop load (~9.2 GiB already used),
this is a real constraint, not a theoretical one. **[M][A]**

### 6.5 Residency transaction mechanics (verified)

The service path implements:

- **Partial residency**: compute the delta between active and target layer sets; preserve
  shared layers, read/transfer only missing layers, remove obsolete layers. **[V]**
- **Delta commit**: one native commit applies the replacement atomically after graph
  invalidation. **[V]**
- **Standby**: recently removed layers are retained in a bounded VRAM cache and can be
  promoted without re-reading. **[V]**
- **Double-buffered pipeline**: prepare the next selection in a pending slot, submit one
  asynchronous transfer, commit after compute. **[V]**
- **Allocation reuse**: best-fit pool; measured 4 allocations retained across cycles. **[M]**

| 2 | 0.0 | 0.0 | 4, 5 | 0.30 | 647.0 |
| 3 | 0.0 | 0.0 | 0, 1 | 0.28 | 639.2 |
| 4 | 0.0 | 0.0 | 4, 5 | 0.31 | 634.1 |

Prefetch totals: 1,437,196,288 B prepared, 280,248,320 B committed, 1,156,947,968 B
served from standby, 0 wasted, hit rate 1000‰. End-to-end including transitions:
5.306 tok/s. **[M]**

Interpretation: the standby cache is doing exactly what it should for repeating
selections. The first transition is expensive (cold read + transfer); subsequent
transitions are effectively free. This is a genuine, validated optimization. **[M]**

Caveat: the benchmark alternates two fixed selections, which is the best case for a
standby cache. Real generation changes layers only at explicit transition points, and
the predictor's benefit on non-repeating patterns is not established here. **[A]**

### 6.7 The missing capability: expert granularity

DeepSeek2's per-layer expert tensors:

```
blk.1.ffn_down_exps.weight  196,083,712 B
blk.1.ffn_gate_exps.weight  103,809,024 B
blk.1.ffn_up_exps.weight    103,809,024 B
blk.1.ffn_gate_inp.weight       524,288 B
blk.1.ffn_{down,gate,up}_shexp  ~11.2 MB total
```

Expert-named tensor bytes total 7,578.1 MB of the 10,364,416,768-byte file. Six of 64
experts are active per token. Whole-layer staging would transfer all 403 MB of layer 1's
expert tensors to use roughly 6/64 of them. Expert-aware staging could reduce that by
roughly an order of magnitude, before accounting for routing reuse. **[M][E]**

No API exists to observe the router's selection or to stage one expert. This is the
single largest gap between the current runtime and a credible MoE strategy. **[V]**

### 7.2 Dense overflow: the arithmetic of the floor

For a dense model whose weights exceed usable page cache, each decode token must read
the non-resident portion. The throughput ceiling is approximately:

```
tok/s <= effective_read_bandwidth / non_resident_weight_bytes
```

Observed: 19.2 GB read over 12.56 s ≈ 1.53 GB/s average; 10.2-10.4 s per steady token with
~10 GB non-resident implies an effective ~0.9-1.0 GB/s during steady decode. **[M][E]**

Consequences:

- 20B Q4 (13.1 GB) with 8 GiB cap: the documented 7.64 GiB resident / 7.72 s single
  token is consistent with this model. It executes, but it is not interactive. **[V][M]**
- 32B Q4 (19.85 GB) with ~10 GB resident: ~0.1 tok/s. **[M]**
- 90 GB dense Q4 with ~10-12 GB resident: ~0.01-0.03 tok/s at 1-3 GB/s. **[E]**
- 250 GB dense Q4: not feasible on this hardware; even one token requires ~240 GB of
  reads. **[E]**

This is the central capacity finding: **dense overflow scales badly because bytes read
per token scale with model size.** Placement and threading cannot change the numerator.

### 7.3 MoE: the only structurally different case

DeepSeek2 activates 6 of 64 experts. If only active experts are read:

- Expert bytes per layer ≈ 403 MB total; active fraction ≈ 6/64 ≈ 9.4%, or ~38 MB/layer.
- 26 MoE layers × ~38 MB ≈ 1 GB of expert data per token, versus 7.58 GB for all experts.
- Plus attention/shared/norms ~2.8 GB, which can remain resident.
- At 1-3 GB/s, that is ~0.3-1 s/token if routing is stable and prefetch works. **[E]**

Measured native CPU execution already achieves 0.26-0.70 s/token with 2.9 GB RSS,
because the OS page cache holds the hot set and routing is biased. That is evidence the
idea is plausible, not proof that explicit expert staging would beat demand paging. **[M][H]**

The risk is routing variability: if the active set changes every token and spans many
experts, storage traffic approaches the full expert payload. Any design must measure
routing entropy and cache hit rate before claiming a win. **[H]**

### 7.4 GPU behavior

SmolLM2 full GPU: 469.91 tok/s median, CUDA0 model 103.74 MB, KV 5.9 MB, compute
50.92 MB. CUPTI (graphs disabled): 18,577 kernels, 94.29 ms busy over 195.29 ms span
(48.3%), 25.74 ms memcpy / 110.1 MB, throughput 162.1 tok/s. With graphs: 176.0 tok/s,
but only 1,327 valid kernel timestamps. **[M]**

Interpretation:

- At 135M parameters and batch 1, the GPU is substantially launch/synchronization-bound;
  roughly half the timeline is not kernel execution.
- Disabling graphs for profiling costs ~8% throughput and changes behavior, so it must
  not be a production setting.
- For larger models and prefill batches, kernel busy fraction should rise; this audit did
  not measure a large-model GPU-resident decode because 4 GB VRAM cannot hold one. **[A]**

The 7B staged run shows CUDA0 compute only 1.35 MB and model 0 bytes, confirming staged
layers are separate buffers and the GPU is used for a small slice of the graph. **[M]**

### 7.5 Staging and overlap

Historical measurements in the repository report that overlapping transfer with compute
did **not** improve end-to-end latency: 790.2 ms overlapped vs 728.1 ms synchronized over
five Qwen cycles, because concurrent DMA reduced compute throughput. **[M]**

This audit's staging-cycle run did not re-test overlap A/B; it used the validated
pipeline path and measured 5.306 tok/s including transitions. The negative overlap result
should be treated as a real constraint until a better chunking/priority scheme is tested.
Do not assume "async is faster." **[M][A]**

### 7.6 Loading and TTFT

- SmolLM2 load is sub-second; full GPU TTFT 3.9 ms, CPU 9.8 ms. **[M]**
- Qwen 7B staged load: 547-4,223 ms depending on cache state; TTFT 199.9-385.8 ms. **[M]**
- 32B load (mmap no-prefetch) 325-382 ms, but prefill 11.7 s for 2 tokens. Loading is not
  the bottleneck; first compute is. **[M]**
- DeepSeek2 load 317-322 ms, prefill 2.34 s for 2 tokens. **[M]**

TTFT for oversized dense models is dominated by the first full pass over weights, not by
file open or metadata parsing.

- Single machine, desktop session, load average ~2.4, ~9.2 GiB RAM already in use.

- Expert routing entropy over a long generation (no hook).

### 8.10 Benchmark protocol for future work

Every performance claim should record:

1. Model file path(s), SHA-256 or size, architecture, quantization.
2. Prompt tokens, generation tokens, context length, batch/ubatch, KV dtype, flash attention.
3. Backend, device, `gpu_layers`, staged layers, thread count, affinity.
4. Driver/CUDA/llama.cpp pin and build flags.
5. Warm/cold state and how it was established (without dropping global caches).
6. TTFT, prefill tok/s, decode tok/s, total wall time.
7. Peak RSS, peak VRAM, native buffer breakdown.
8. Bytes read, host/device transfer bytes, major faults.
9. Allocation count, standby hit rate, transition time.
10. Success/failure and exact error text.

Use at least five repetitions with median and IQR, interleave A/B configurations to
cancel drift, and never compare a cold run to a warm run. Small models are for
correctness and regression speed only; they do not predict 20B+ behavior.

## 10. Research findings and technical references

### A. CPU/GPU placement and heterogeneous execution

**Established:** transformer layers are heterogeneous in cost; attention and FFN have
different arithmetic intensity; CPU/GPU split should be measured, not derived from
parameter counts. SMT siblings usually hurt CPU GEMM throughput because the kernels are
already SIMD-saturated.

**Adaptation for RAMforge:** keep the physical-core default, but calibrate the actual
thread count per model class and record it with a hardware/config key. The measured
1.46-1.67x staged-decode advantage is large enough to justify a persisted calibration,
but the variance means a fixed constant is wrong.

**Speculative:** per-layer placement based on measured layer time. This requires
per-layer timing that the current graph abstraction does not expose cheaply; defer until
profiling is reliable.

### B. Memory residency and overflow

**Established:** keep/transfer/recompute is the correct decision framework, but
recomputation is almost never valid for weights. For weights, the choice is resident vs
transfer. Caches help only when reuse is high; a standby cache is a bet on selection
locality.

**Adaptation:** the current delta + standby design is the right structure. The next
improvement is not a more complex predictor; it is reducing bytes per transition
(expert granularity) and making transitions overlap with useful compute without
sacrificing kernel throughput.

**Speculative:** multi-step lookahead beyond one pending selection. The negative overlap
result suggests the bottleneck is DMA/compute contention, not scheduling depth. Adding
depth without fixing contention is likely wasted VRAM.

### C. Storage and data movement

**Established:** sequential coalesced reads beat parallel small reads on NVMe for this
workload; page cache is effective when the working set fits. `O_DIRECT`/`io_uring` are
not automatically faster and can bypass useful caching.

**Measured in repository history:** coalesced 59.9 ms vs 61.0/83.5 ms at concurrency 2/4;
direct pinned reads cut Qwen 4-layer prep 276→178 ms; async host reads improved medians
~7%.

**Adaptation:** keep coalesced reads as default; use concurrency only when outstanding
bytes and NVMe queue depth justify it. Measure read amplification per token, not just
throughput.

### D. MoE-specific opportunities

**Established:** MoE decouples total parameters from active compute. The active set is
chosen per token by a router; locality depends on the model and prompt. Expert tensors
dominate file size in DeepSeek2 (7.58/10.36 GB).

**Adaptation:** the correct unit of residency is the expert, not the layer. Whole-layer
staging is actively harmful for MoE because it copies inactive experts. The runtime needs
(a) a routing observation hook, (b) expert-granular staging or a way to keep all experts
mapped and rely on page cache, and (c) accounting for active vs total bytes.

**Speculative:** predicting the next token's experts from router logits. Top-k routing is
often stable across adjacent tokens, but this must be measured before building a
predictor. A simple "prefetch last token's experts" policy is the right first experiment.

### E. KV cache and attention

**Established:** KV bytes/token = layers × KV heads × head_dim × 2 × bytes/element.
GQA/MQA reduce KV dramatically. Quantized KV (Q8_0/Q4_0) is supported by llama.cpp and
is mathematically a block-wise affine quantization; quality loss is usually small at Q8
and measurable at Q4.

**Measured:** 57,356 / 30,476 / 16,140 B/token for F16/Q8/Q4 on Qwen 7B, matching the
formula within 0.02% (57,356 vs 57,344 B/token). At 131k context this is 7.52/4.00/2.12 GB. **[M]**

**Adaptation:** expose KV dtype in the plan and adapter; default to F16 for compatibility
but allow Q8 for long context. Pair with flash attention where supported. Do not confuse
this with the deferred Context Engine.

**Speculative:** mixed KV precision per layer (e.g., Q4 for early layers, Q8 for late).
Plausible but needs quality evidence; not a first step.

### F. Hardware calibration and adaptive configuration

**Established:** simple, explainable calibration beats learned policies for a single
machine. Measure thread count, transfer bandwidth, storage read bandwidth, and placement
throughput; persist with a key that includes CPU model, GPU model, driver, backend,
model fingerprint, and relevant runtime options.

**Adaptation:** the existing `calibrate-hw` and profile persistence are the right
foundation. The missing piece is enforcement: the calibrated values should feed the
actual plan and be visible as "measured" rather than "requested." Invalidate on any key
change; never silently reuse a profile across a driver or backend change.

**Speculative:** online adaptation during generation. Too risky and too complex for the
current objective; defer.

## 11. New optimization hypotheses

Each hypothesis states a mechanism, a falsifiable experiment, a positive signal, and a
kill criterion. None is a recommendation to implement before the experiment.

### H1. Expert-aware MoE residency beats whole-layer staging

**Mechanism:** stage only the experts selected by the router (plus shared experts and
attention, which can stay resident). DeepSeek2 selects 6/64 experts; expert tensors are
7.58 GB of 10.36 GB.

**Experiment:** add a read-only router-observation hook (top-k expert ids per layer per
token). For a fixed prompt, log the active set over 256 tokens. Compute:
(a) bytes of unique experts touched, (b) bytes per token if staging the active set,
(c) overlap between consecutive tokens.

**Positive signal:** active-set bytes per token < 30% of whole-layer bytes and
consecutive-token overlap > 50%.

**Kill criterion:** active set spans > 50% of experts per token, or overlap < 10%,
making per-token staging read as much as the full layer.

**Dependency:** native router hook; no such API today.

### H2. Dense overflow throughput is predictable from read amplification

**Mechanism:** decode tok/s ≈ effective bandwidth / non-resident bytes per token. If true,
capacity planning can be done from model size, RAM budget, and measured NVMe bandwidth
without running the model.

**Experiment:** run 20B/32B under two RAM budgets (e.g., 6 GiB and 10 GiB) and measure
bytes read per token via `/proc/self/io` plus `/usr/bin/time -v`. Compare predicted vs
observed tok/s.

**Positive signal:** prediction within 30% across budgets.

**Kill criterion:** read amplification varies by >3x for reasons not explained by working
set, indicating page-cache behavior dominates and the simple model is unusable.

### H3. Q8 KV is nearly free in throughput and halves KV bytes

**Mechanism:** Q8_0 KV reduces bytes/token 1.88x with minor dequantization cost.

**Experiment:** Qwen 7B CPU and partial-GPU, 8k context, same prompt, F16 vs Q8 vs Q4;
measure prefill/decode tok/s, state bytes, and a small quality probe (top-1 agreement and
perplexity on a fixed text).

**Positive signal:** Q8 within 5% of F16 throughput and ≥95% top-1 agreement; Q4 within
15% throughput and acceptable quality for the target use.

**Kill criterion:** Q8 decode regresses >15%, or quality loss is material at the target
context.

### H4. Physical-core default is worth ≥30% on staged decode under controlled load

**Mechanism:** staged decode is CPU-GEMM-bound; SMT siblings contend for execution units.

**Experiment:** interleaved A/B/A/B, 5 repetitions each, CPU affinity pinned, background
load recorded, warm model, same staged selection.

**Positive signal:** 6-thread median ≥1.3x 12-thread median with non-overlapping IQRs.

**Kill criterion:** distributions overlap or the effect disappears when load is low,
meaning the earlier result was contention noise.

### H5. GPU gaps are launch-bound at small batch, not kernel-bound

**Mechanism:** 48% kernel busy on SmolLM2 full GPU with batch 1 indicates launch/sync
overhead; larger batch should raise utilization.

**Experiment:** vary prefill batch (1/32/128/512) and measure CUPTI busy/span plus
prefill tok/s. Keep graphs enabled for the throughput measurement and use a separate
graph-disabled run only for attribution.

**Positive signal:** busy/span rises above 70% at batch ≥128 and prefill tok/s scales
sublinearly but positively.

**Kill criterion:** busy/span stays flat, indicating a fixed serialization unrelated to
batch.

### H6. Staging overlap can win with the right chunking

**Mechanism:** the historical negative result (790.2 vs 728.1 ms) may be due to
transfer granularity/priority, not an inherent DMA/compute conflict.

**Experiment:** sweep chunk size (layer vs sub-layer tensor groups) and stream priority;
measure end-to-end cycle time and kernel slowdown during transfer.

**Positive signal:** overlapped median < synchronized median by >5% with no kernel
slowdown >10%.

**Kill criterion:** any overlap configuration slows compute enough to lose end-to-end,
reproducing the historical result. Then stop investing in overlap.

### H7. `run` thread bug accounts for most CPU-path user-visible slowness

**Mechanism:** `n_threads: 1` in the ForgeCore run path.

**Experiment:** patch only the thread value in a scratch build, run the same prompt via
`run --backend forgecore` at 1 vs 6 threads, measure decode tok/s.

**Positive signal:** ≥3x improvement at 6 threads.

**Kill criterion:** native ignores the value or the workload is memory-bound enough that
threads do not matter.

  CLI `support`/`run` error text. No native change.
- **Dependencies:** none.
- **Capacity impact:** unlocks 15.7B total / 6-active MoE; measured 2.9 GB RSS.
- **Decode impact:** ~2.2 tok/s measured on CPU; more with threads/KV tuning.
- **TTFT / prefill:** 2.34 s for 2 tokens at 64 ctx; improves with batch.
- **Memory/storage:** 10.36 GB file, 7.58 GB expert bytes; page-cache dependent.
- **Complexity:** XS-S.
- **Risks:** architecture-specific tokenizer/chat-template mismatch; MoE output quality
  must be validated, not assumed.
- **Measurements:** prefill/decode tok/s, RSS, major faults, top-1 agreement vs native.
- **Acceptance:** `ramforge run --backend forgecore` produces a coherent continuation;
  `support` reports it; regression tests cover the gate.
- **Upstream:** no.
- **Confidence:** high.

#### T1.2 Forward plan threads in `run --backend forgecore`

- **Capacity impact:** none.

- **TTFT:** improves.
- **Memory/storage:** negligible.
- **Complexity:** XS.

- **Acceptance:** `run` matches `benchmark` thread behavior.
- **Upstream:** no.

#### T1.3 Expose and forward KV dtype, flash attention, batch/ubatch, offload

- **Problem:** adapter forwards 3 fields; everything else is default.
- **Current status:** forgeCORE already supports the options; RAMforge hides them.
- **Approach:** extend `ForgeCoreContextOptions` with `type_k`, `type_v`, `flash_attn`,

- **Capacity impact:** Q8 KV reduces KV 1.88x; Q4 3.55x. At 131k on Qwen 7B: 7.52→4.00→

- **Decode impact:** small; measure Q8 overhead.
- **TTFT / prefill:** real batch/ubatch enables faster prefill.
- **Memory/storage:** lower KV footprint; batch increases compute buffer.
- **Complexity:** S.

- **Acceptance:** plan JSON reports the dtype actually used; Q8/Q4 decode succeeds;

- **Upstream:** no for plumbing; llama.cpp already supports the options.
- **Confidence:** high.

### Track 2 — Major inference optimizations

#### T2.1 Expert-aware MoE residency (highest potential)

- **Problem:** whole-layer staging copies all 64 experts; only 6 are active.
- **Current status:** impossible; no routing hook or expert staging.
- **Approach:** phase 1, read-only router observation (expert ids per layer/token) via a
  native callback; phase 2, measure active-set entropy and reuse; phase 3, expert-granular
  staging or prefetch, only if phase 2 justifies it.
- **Boundaries:** native `llama-graph`/`llama-model`, forgeCORE safe wrapper, RAMforge
  residency policy. This crosses all three layers.
- **Dependencies:** T1.1, native API work.
- **Capacity impact:** potentially 5-10x fewer bytes per MoE token; could make 30B-100B
  MoE plausible at 2-4 GB active working set.
- **Decode impact:** potentially large; unproven.
- **TTFT:** improves if prefill can batch expert reads.
- **Memory/storage:** trades VRAM/standby for storage reads; routing variability is the
  risk.
- **Complexity:** L.
- **Risks:** aliasing/lifetime across graph replays; expert selection happens inside the
  graph; prefetch may arrive too late; routing may be unstable.
- **Measurements:** active-set bytes/token, consecutive-token overlap, cache hit rate,
  decode tok/s vs whole-layer staging.
- **Acceptance:** ≥2x decode improvement on DeepSeek2 with no correctness change, or a
  documented negative result that closes the line of work.
- **Upstream:** likely yes (or a local patch consistent with the existing 12-file set).
- **Confidence:** medium (mechanism strong, implementation uncertain).

#### T2.2 Measured placement/thread calibration with enforcement

- **Problem:** defaults are heuristics; plan values are not enforced; profiles can go stale.
- **Approach:** bounded calibration of threads, gpu_layers, staged layers, and transfer
  path; persist with a key (CPU, GPU, driver, backend, model fingerprint, options);
  invalidate on mismatch; feed the service plan.
- **Boundaries:** `hw_calibration.rs`, `runtime_calibration.rs`, `calibration*.rs`,
  `execution_profile.rs`, service.
- **Dependencies:** T1.3 for KV/batch dimensions.
- **Capacity impact:** indirect (better placement fits more layers).
- **Decode impact:** 1.2-1.7x plausible from threads/placement alone.
- **TTFT:** modest.
- **Complexity:** M.
- **Risks:** overfitting to noisy desktop conditions; calibration time; stale profiles.
- **Acceptance:** calibrated config beats default by ≥10% median on two model classes,
  with reproducible invalidation behavior.
- **Confidence:** medium-high.

#### T2.3 Storage-aware dense execution beyond mmap

- **Problem:** dense overflow relies on OS demand paging; no control over read order or
  eviction.
- **Approach:** explicit per-layer prefetch with measured read amplification; consider
  sequential read-ahead aligned to layer order; evaluate whether a RAM-resident hot set
  plus explicit streaming beats mmap. Do not build a new tensor engine.
- **Boundaries:** `host_staging.rs`, `page_residency.rs`, `inference_service.rs`,
  native prefetch APIs.
- **Dependencies:** none, but requires reliable per-token I/O measurement.
- **Capacity impact:** modest; makes large dense models more predictable, not interactive.
- **Decode impact:** target 1.2-2x on 20B/32B if read amplification can be reduced.
- **TTFT:** improves with ordered prefetch.
- **Complexity:** M-L.
- **Risks:** prefetching evicts useful pages; page cache is shared; gains may be small.
- **Acceptance:** ≥20% decode improvement on 20B under a fixed cgroup, or a clear negative
  result.
- **Confidence:** medium.

#### T2.4 Batch/prefill tuning and TTFT

- **Problem:** batch is not forwarded; prefill of oversized models is seconds.
- **Approach:** forward batch/ubatch (T1.3), sweep prefill batch on Qwen/SmolLM2, measure
  TTFT and compute-buffer growth; choose a default that fits VRAM.
- **Boundaries:** adapter + service + plan.
- **Dependencies:** T1.3.
- **Capacity impact:** none directly; larger batch may need more VRAM.
- **Decode impact:** none.
- **TTFT:** potentially 2-4x on prefill.
- **Complexity:** S-M.
- **Risks:** batch that exceeds compute buffer causes OOM; validate before apply.
- **Acceptance:** measured TTFT reduction with no decode regression.
- **Confidence:** high (native support exists).

#### T2.5 Resolve the staging-overlap question

- **Problem:** historical overlap loses to synchronous transfer.
- **Approach:** chunk-size and stream-priority sweep; measure kernel slowdown during DMA.
  If it still loses, document and stop.
- **Boundaries:** native staging/pending API, service pipeline.
- **Dependencies:** none.
- **Capacity impact:** none.
- **Decode impact:** target 5-10% if a win exists.
- **Complexity:** M.
- **Risks:** wasted effort; negative result is acceptable and valuable.
- **Acceptance:** a clear A/B result with IQRs, either direction.
- **Confidence:** low-medium.

#### T2.6 Unify static offload and dynamic staging

- **Problem:** staging is rejected unless the plan is CPU-only, so the common best
  configuration (some layers static on GPU, others staged on demand) is impossible.
- **Current status:** explicit service error at `inference_service.rs:669-674`; staged
  buffers use a separate CUDA device while the model runs on CPU.
- **Approach:** allow a hybrid plan whose static layers use the main device and staged
  layers use the staging device; account for both budgets; validate graph invalidation
  and lifetime across both placements. Start with measurement of whether the current
  split is a native limitation or a service policy.
- **Boundaries:** `inference_service.rs`, `runtime_plan.rs`, `forgecore.rs`; native
  placement may need a second device/context.
- **Dependencies:** T1.4 (truthful plans), T2.2 (budget calibration).
- **Capacity impact:** medium-high: VRAM currently used for static layers is unavailable
  to staging, and vice versa.
- **Decode impact:** medium; the best split may be neither pure CPU nor pure GPU.
- **TTFT:** moderate.
- **Memory/storage:** requires combined VRAM budgeting; risk of overcommit.
- **Complexity:** S-M if policy-only, L if native placement must change.
- **Risks:** two contexts/devices may duplicate compute buffers; lifetime/aliasing bugs.
- **Measurements:** VRAM used, staged hit rate, decode tok/s for CPU-only vs hybrid vs
  hybrid+staging on Qwen 7B.
- **Acceptance:** a measured configuration that beats both pure strategies, or a
  documented native limitation.
- **Confidence:** medium.

### Track 3 — forgeCORE capabilities

- **Problem:** safe API hides KV/batch/flash/offload controls.
- **Approach:** add the fields to `ForgeCoreContextOptions`; add a `context_capabilities()`

- **Confidence:** high.

#### T3.2 Per-layer/per-tensor placement and memory introspection

- **Problem:** service can see aggregate buffers and tensor storage, but not enough to
  reason about per-layer residency during a graph.
- **Approach:** expose existing native counters through a stable schema; add per-layer

- **Boundaries:** forgeCORE wrapper; native already has most data.
- **Complexity:** S-M.
- **Acceptance:** a plan can state exactly which layers are where before decode.
- **Confidence:** high.

#### T3.3 Expert routing observation and expert residency API

- **Problem:** hard blocker for MoE.
- **Approach:** native callback for selected expert ids per layer/token; expert-granular
  stage/prefetch/evict if feasible; forgeCORE safe wrapper with lifetime guarantees.
- **Boundaries:** native + forgeCORE + RAMforge policy.
- **Complexity:** L.
- **Acceptance:** read-only observation first; staging only after H1 passes.
- **Confidence:** medium.

#### T3.4 Graph-preserving profiling

- **Problem:** CUPTI graph mode loses 93% of kernel timestamps; disabling graphs changes
  behavior.
- **Approach:** range-based profiling (CUPTI activity ranges / NVTX) that records graph
  launches and node execution without disabling graphs; or per-graph aggregate timing.
- **Boundaries:** `forgeCORE/tools/cupti_trace.cpp`.
- **Complexity:** M.
- **Acceptance:** kernel-busy attribution with graphs enabled, validated against the
  graph-disabled run on a small model.
- **Confidence:** medium.

### Track 4 — Experimental research

#### T4.1 Expert-prefetch predictor

Use last-token expert ids to prefetch next-token experts; measure hit rate and decode
gain. Kill if routing entropy is high. Depends on T3.3.

#### T4.2 Mixed KV precision per layer

Q4 for early layers, Q8 for late; measure quality and bytes. Only after T1.3 and a
quality harness exist.

#### T4.3 Transfer-vs-recompute for intermediate buffers

Restrict to disposable activations/workspaces, never weights. Likely low value; keep as
a bounded experiment.

#### T4.4 Long-context KV + flash attention on CUDA

Measure 8k-32k context on the 4 GB GPU with Q8 KV and flash attention; determine the
practical context ceiling for a 7B model. This is capacity-relevant but bounded by VRAM.

#### T4.5 Cgroup-enforced native memory budgets

Extend the existing `--enforce-ram` work to cover native allocations and staging pools,
so out-of-core claims are enforceable rather than advisory. This is reliability work, not
raw throughput, but it underpins credible capacity claims.

## 13. Deferred features and explicit non-goals

The following are deliberately out of scope and should not be started under this
objective:

- **Advanced Context Engine / retrieval / long-term memory.** KV management is in scope;
  context construction is not.
- **Autonomous file indexing or knowledge management.** No.
- **Agent orchestration, tool use, planning loops.** No.
- **Autonomous multi-model routing or model selection.** No.
- **Vector databases or persistent semantic stores.** No.
- **New HTTP services or microservices** without a concrete inference requirement.
- **A competing tensor engine or graph scheduler.** llama.cpp/ggml owns this.
- **Direct llama.cpp FFI in RAMforge or a `forge-sys` dependency.** Preserve the boundary.
- **Machine-learning-based performance prediction.** Simple measured policies first.
- **Speculative decoding / draft models.** Potentially useful later, but not before the
  basic capacity and KV/batch plumbing is correct.
- **Weight recomputation as an overflow strategy.** Not valid for model weights.

Any proposal in these areas should be rejected unless it demonstrably improves model
capacity, decode throughput, or reliability of oversized execution.

## 14. Risks, unresolved questions, and required decisions

### 14.1 Risks

| Risk | Impact | Mitigation |
|---|---|---|
| Enabling `deepseek2` without adequate validation | Wrong/unsafe output presented as supported | Gate on tokenizer/logit/continuation tests; keep explicit failure |
| Quantized KV incompatible with a model's head dim | Context open or decode failure | Validate block divisibility; fail explicitly with a clear message |
| Physical-core default hurts under low load or with batch | Throughput regression | A/B with IQR; allow explicit override; calibrate per model class |
| Batch increase exhausts VRAM | OOM or plan rejection | Compute buffer estimate before apply; clamp to budget |
| Expert staging aliasing/lifetime bug | Corruption or crash | Read-only observation first; reuse existing quiescence/invalidate contract |
| Calibration profile staleness | Wrong placement after driver/model change | Strict invalidation key; never auto-reuse across keys |
| Page-cache measurements mislead | Overstated capacity claims | Report bytes read and residency explicitly; never call mmap "streaming" |
| Background desktop load | Non-reproducible benchmarks | Record load; interleave A/B; report IQR; avoid absolute claims |

### 14.2 Unresolved questions

1. Can native llama.cpp expose per-token expert selection without destabilizing graph
   replay? Unknown; requires a prototype.
2. Does expert-aware staging beat OS page-cache demand paging on this NVMe? Unproven.
3. What is the real long-context quality cost of Q4 KV on Qwen/DeepSeek? Not measured.
4. How much of the staged-decode thread gain survives on an idle machine? The direction
   is consistent; the magnitude is not.
5. Can graph-preserving profiling recover enough attribution to guide optimization?
6. What is the largest model that can be *interactive* (≥1 tok/s) here? Current evidence
   suggests ~10-15B dense at best with aggressive KV/placement, or a sparse MoE.
7. Does the 4 GB GPU help oversized decode at all, or only prefill/small models? The
   staged Qwen run used a tiny compute slice; more evidence is needed.

### 14.3 Required decisions

- **D1:** Approve adding `deepseek2` as a validated forgeCORE architecture (T1.1).
- **D2:** Approve widening the RAMforge adapter to forward KV/FA/batch/offload (T1.3),
  with explicit validation and no silent defaults.
- **D3:** Decide whether the next milestone is "capacity via MoE" (T2.1/T3.3) or
  "throughput and honesty via KV/batch/calibration" (T1.3/T2.2/T2.4). The audit recommends
  the latter first, because it is cheaper and makes the former measurable.
- **D4:** Decide whether native expert-routing work is permitted in the pinned checkout.
  If not, MoE stays at whole-layer/page-cache behavior and 180B-class claims remain
  unsupported.
- **D5:** Approve a benchmark harness that records the fields in §8.10 and refuses to
  compare incomparable runs.
